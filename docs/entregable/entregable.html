1Descripción del proyecto y sus módulos

1.1 El sistema

AgroIA es una plataforma web para controlar, monitorear y analizar un sistema de riego inteligente. Cada parcela tiene una estación con conexión a internet y varios nodos de suelo que se comunican con ella por radio (LoRa). La estación envía las lecturas de los sensores al servidor y recoge las órdenes de riego que el agricultor da desde la aplicación web.

ComponenteTecnologíaFunción
BackendPython · Flask · SQLAlchemy · JWTAPI REST: autenticación, usuarios, parcelas, nodos, comandos, alertas, bitácora y reportes.
FrontendReact · ViteInterfaz web para el administrador y los agricultores.
DatosMySQL e InfluxDBMySQL guarda usuarios, parcelas y eventos; InfluxDB guarda las lecturas de los sensores.
DispositivosESP32 y simulador en PythonEstación y nodos de suelo que miden y ejecutan el riego.

Las pruebas de este proyecto se hicieron sobre el backend, porque ahí están las reglas de negocio del sistema. El backend está escrito en Python, por lo que el framework utilizado es PyTest.

2Estrategia y entorno de pruebas

FrameworkPyTest 8.4.2 sobre Python 3.9.1
AislamientoCada prueba crea una aplicación Flask nueva con SQLite en memoria; ninguna prueba depende de otra ni necesita MySQL.
Dependencias externasEl envío de correo (SMTP) e InfluxDB se sustituyen por dobles de prueba (unittest.mock). Un fixture bloquea smtplib para que sea imposible enviar un correo real.
TiempoLas fronteras de tiempo (20 minutos, 10 minutos, 7 días, cooldown) se prueban con un reloj simulado, por lo que el resultado no depende de la hora ni de la velocidad del equipo.
Datos de pruebaFixtures de tests/conftest.py: 4 usuarios base (2 administradores y 2 agricultores) y funciones para crear parcelas, nodos y sesiones.
Casos múltiples@pytest.mark.parametrize ejecuta la misma prueba con varios valores (por ejemplo 11, 12, 128 y 129 caracteres).

def alterar_firma(token):
    """Cambia un carácter interior de la firma de un token firmado.

    No se altera el último carácter: en base64 sus 2 bits finales no se usan,
    por lo que el token podría seguir siendo válido y la prueba sería inestable.
    """
    posicion = len(token) - 5
    sustituto = "A" if token[posicion] != "A" else "B"
    return token[:posicion] + sustituto + token[posicion + 1:]

7Conclusiones

Importancia del testing

Sin pruebas automatizadas, comprobar que AgroIA funciona exige levantar todos los servicios con Docker y probar a mano desde el navegador. Con las pruebas unitarias, comprobar 205 casos toma menos de medio minuto y no requiere MySQL, InfluxDB ni un dispositivo conectado. Lo más valioso no fue confirmar lo que ya funcionaba, sino lo que las pruebas descubrieron: tres defectos reales del backend y un archivo de pruebas de integración que había quedado desactualizado tras un cambio en la autenticación. En un sistema que abre y cierra válvulas de riego, un error en una regla (por ejemplo, quién puede ordenar un riego o cuándo caduca un comando) tiene consecuencias físicas, así que conviene que una máquina lo verifique en cada cambio.

Retos y aprendizajes

  • Aislar las dependencias. El backend usa MySQL, InfluxDB y correo SMTP. Aprendí a sustituir MySQL por SQLite en memoria y a reemplazar InfluxDB y el correo con dobles de prueba, cuidando que ninguna prueba pudiera enviar un correo real.
  • Probar fronteras de tiempo. Reglas como «el enlace caduca a los 20 minutos» no se pueden probar esperando 20 minutos. La solución fue simular el reloj, lo que permitió verificar el segundo exacto en que cambia el resultado (1200 s vigente, 1201 s caducado).
  • Pensar en los límites. La mayoría de los errores posibles están en los bordes: > contra >=, 12 contra 11 caracteres. Usar parametrize para probar el valor mínimo, el máximo y el primero fuera de rango resultó más útil que escribir muchas pruebas del caso normal.
  • Desconfiar de una prueba que pasa. Para saber si las pruebas servían, introduje errores a propósito en el código; solo cuando las pruebas fallaron con cada error tuve confianza en ellas.
  • Una prueba inestable es peor que no tenerla. Una prueba que alteraba el último carácter de un token fallaba aproximadamente 1 de cada 16 ejecuciones: en base64 los últimos 2 bits de ese carácter no se usan y a veces el token «alterado» seguía siendo válido. Se corrigió alterando un carácter interior de la firma y se repitió 30 veces sin fallos.
  • El entorno también cuenta. Con Python 3.9.1 la versión fijada de cryptography no cargaba y hubo que usar la 41.0.7 en el entorno de pruebas; el contenedor del proyecto usa Python 3.11 y no tiene ese problema.

Calidad lograda

  • 70 pruebas nuevas en 6 módulos (191 casos con sus variantes), todas clasificadas como caso normal, de error, límite o regla de negocio.
  • 202 de 205 casos en PASSED y ninguno en FAILED; los 3 restantes son defectos documentados, no pruebas inestables.
  • Cobertura de entre 85 % y 97 % en las rutas de los módulos probados, con excepción de autenticación (66 %), donde falta probar la edición del perfil.
  • Las 6 alteraciones introducidas a propósito fueron detectadas.

La calidad lograda es buena en las reglas de negocio que se probaron, pero no es total: la cobertura global del backend es de 61 % porque la recepción de lecturas de sensores, la bitácora y el servicio de correo siguen sin pruebas. El siguiente paso sería corregir los tres defectos abiertos, cubrir esos módulos y ejecutar la suite automáticamente en cada push al repositorio.
